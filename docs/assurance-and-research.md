# Assurance and research considerations

This note maps the financial-sector LLM risks in the project brief to the controls that exist in this local demonstrator and the work that remains necessary before a controlled deployment. These controls reduce risk; they do not prove regulatory compliance or make model outputs authoritative.

| Challenge | Current design/control | Residual risk and recommended next step |
|---|---|---|
| Hallucinations | RAG retrieves scoped evidence before Compliance, Security/Privacy, SDLC, and Documentation calls. Agents receive IDs and source metadata and are told to cite only retrieved records. Per-agent citation validation and deterministic compliance downgrades expose unsupported evidence. | Retrieval can miss applicable evidence; models can misinterpret passages or invent uncited text. Use approved primary sources, retrieval evaluation, adversarial tests, and reviewer sign-off. |
| Explainability | Requirements retain source excerpts; classifications expose dimensions and confidence; findings carry evidence IDs; SDLC candidates include rationale; audit records contain stage timestamps, output hashes, and evidence IDs. | Confidence scores are model estimates, not calibrated likelihoods. Stage hashes are not signed, immutable, or a full input/output transcript. Add calibrated measures and a protected audit service for regulated deployment. |
| Sensitive financial data | Browser and server mask long digit sequences, email addresses, and common secret-style values before model calls and persistence. Workspaces and analysis reads are account-scoped. | Regex masking is incomplete and can over-mask. It does not detect all account identifiers, names, addresses, free-text financial detail, or context. Do not enter real customer information; use approved DLP/classification and retention controls for production. |
| Bias and fairness | Requirements and risk outputs are exposed for human review; no autonomous customer eligibility, credit, or transaction decisions are made by this requirements assistant. | The model and seed corpus can encode bias, especially in requirements for scoring or fraud controls. Add fairness impact questions, representative evaluation, protected-group impact review, and explicit controls for downstream decision systems. |
| Prompt injection | Shared prompts treat descriptions, chat messages, and pasted sources as untrusted data and prohibit following embedded instructions. Sources are passed as text, not executable tools or system prompts. | Prompt framing is not a security boundary and may be bypassed. Add adversarial testing, tool isolation, strict structured-output validation, least-privilege model tools, and human review of retrieved content. |
| Access control | Authentication uses account-scoped SQLite workspaces, hashed passwords, and an HttpOnly, SameSite=Strict session cookie. Analysis, PDF, and approval routes verify ownership. | There are no approver roles/RBAC, email verification, account recovery, admin controls, or network access controls. Anyone able to reach an exposed instance can register. Keep it local or protect it behind appropriate network controls. |
| Regulatory change | Knowledge records carry source, jurisdiction, effective date, and version; embedding cache entries are invalidated when content/version changes. Jurisdiction filtering avoids assuming country aliases. | There is no regulatory update feed, supersession workflow, or source-owner approval process. Maintain primary-source records, designate reviewers, track superseded versions, and rerun affected analyses after changes. |
| Interoperability | Requirements, SRS, acceptance criteria, traceability, evidence references, risks, and SDLC workflow use structured JSON internally; the SRS can be downloaded as PDF. | There are no file imports, ticketing/ALM connectors, structured export formats, or financial messaging/API adapters. Define schemas and controlled adapters (for example OpenAPI or the organization's requirements-management format) before integrating. |
| Human oversight | The Clarification Agent pauses on blocking questions. Every requirement gets an owner-review task; required tasks (for example low-confidence, compliance-gap, validation, or conflict items) must be approved before final owner approval. Approval identity, time, note, and decision are archived. | The signed-in account holder is the only approver; no separation of duties or external audit approval is implemented. Use an organization-approved multi-person approval workflow before operational adoption. |
